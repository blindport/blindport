Client operations

Run blindportd

Connect paid subscriptions to services on one Linux host. One daemon can serve every framed mapping in an account.

Install and verify

Versioned static Linux binaries are available for amd64, arm64, and armv7 from GitHub Releases. Download the binary and matching .sha256 file for the same release, then verify before installation:

{% if blindportd_version != "dev" %}
  • Linux amd64 (checksum)
  • Linux arm64 (checksum)
  • Linux armv7 (checksum)
{% endif %} 
sha256sum -c blindportd-{{ blindportd_version }}-linux-amd64.sha256
sudo install -m 0755 blindportd-{{ blindportd_version }}-linux-amd64 /usr/local/bin/blindportd
blindportd -version

A successful checksum says OK. Do not rename the binary until after verification because the checksum file contains the release filename.

Token and state

The account token is a bearer credential. Put exactly one token in an owner-only regular file; avoid command-line and environment values in production because they can be exposed through process inspection.

install -d -m 0700 "$HOME/.config/blindport" "$HOME/.local/state/blindport"
bash -c 'read -rsp "Blindport token: " token && printf "\n" && \
  printf "%s\n" "$token" | install -m 0600 /dev/stdin "$HOME/.config/blindport/token"'

The state directory stores the client Ed25519 identity and, in routed mode, a WireGuard key. It must be absolute, owned by the daemon user, and inaccessible to group and other users. Back it up as a secret. Production permits one enrolled client identity per account; losing credential.json requires an operator reset before enrollment can be repeated.

Run framed mode

Create at least one active subscription and mapping, then start the agent:

blindportd \
  -backend={{ request.url.scheme }}://{{ request.url.netloc }} \
  -token-file="$HOME/.config/blindport/token" \
  -state-dir="$HOME/.local/state/blindport" \
  -config="$HOME/.config/blindport/config.json"

The backend returns only active subscriptions. Restart the daemon after adding, removing, or changing a subscription.

Static mappings

Use the subscription references shown in the dashboard-generated configuration. The paid product determines TCP or UDP behavior.

{
  "version": 1,
  "mappings": [
    {
      "subscription_id": 123,
      "upstream": "reverse-proxy:443",
      "http_challenge_upstream": "reverse-proxy:80"
    },
    {
      "subscription_id": 456,
      "upstream": "photos:8080"
    }
  ]
}

The file must be a regular, owner-only file, not a symlink. Mapping IDs must be positive and unique. Upstreams use host:port; bracket IPv6 addresses, for example [::1]:8080.

Docker discovery

One long-running agent continuously discovers running containers, registers declared orders, refreshes active provisioning, and starts or stops mappings without a restart.

Pull ghcr.io/blindport/blindportd from GHCR. For production, use the digest-pinned reference in the matching release's blindport-images.env asset. Set DOCKER_GID to the numeric group owner from stat -c '%g' /var/run/docker.sock, and make the mounted token owner-only for UID/GID 10001.

services:
  reverse-proxy:
    labels:
      tech.blindport.mapping.web.product: "relay"
      tech.blindport.mapping.web.domain: "web.relay.blindport.com"
      tech.blindport.mapping.web.billing_term: "monthly"
      tech.blindport.mapping.web.upstream: "reverse-proxy:443"
      tech.blindport.mapping.web.http_challenge_upstream: "reverse-proxy:80"

  blindportd:
    image: ghcr.io/blindport/blindportd:{{ blindportd_version if blindportd_version != "dev" else "latest" }}
    init: true
    restart: unless-stopped
    command: ["--docker"]
    group_add: ["${DOCKER_GID}"]
    environment:
      BLINDPORT_BACKEND_URL: "{{ request.url.scheme }}://{{ request.url.netloc }}"
      BLINDPORT_TOKEN_FILE: /run/secrets/blindport_token
      BLINDPORT_STATE_DIR: /var/lib/blindport
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - /etc/blindport/token:/run/secrets/blindport_token:ro
      - blindport-state:/var/lib/blindport
    read_only: true
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    tmpfs: ["/tmp:size=16m,mode=1777"]

volumes:
  blindport-state:
Docker socket warning: access to the Docker daemon socket is effectively root-equivalent, even when the discovery calls only list containers. Prefer a narrowly authorized socket proxy where practical.

The mapping name is a stable order key. Relay also requires a domain; Port accepts TCP or UDP; IP uses framed delivery. Existing .subscription labels remain supported. With NWC, an eligible new declaration starts one initial payment; without NWC it appears in the dashboard for manual payment. Removing a label stops forwarding but does not cancel service.

Run the agent and targets on a shared Docker network so labeled upstream names resolve. The agent polls every 10 seconds by default; set BLINDPORT_DOCKER_POLL_INTERVAL between 1s and 5m.

Source and support

Review the source code or open an issue. Report security vulnerabilities privately using the repository's security policy.

TLS and HTTP-01

Blindport Relay reads ClientHello SNI and forwards the original TCP stream. Keep the TLS private key and certificate at the origin and configure the TLS service as the mapping's upstream. Blindport does not terminate customer TLS.

For a managed hostname, the optional http_challenge_upstream receives only relay-validated ACME HTTP-01 requests on port 80. It must be a separate plaintext challenge listener. Normal HTTP and all TLS traffic continue to the regular upstream. Customer-owned domains can use their normal DNS-01 workflow.

Customer-owned names must be subdomains with a direct CNAME. Zone apexes, wildcard claims, CNAME flattening, and CDN-proxied records are not supported. Keep the record in DNS-only mode so Blindport can verify it before each invoice.

Routed WireGuard mode

WireGuard is available only for Blindport IP orders configured for routed delivery. It is separate from framed mappings and Docker discovery. Create root-owned credential and state paths because the agent requires network administration capability:

sudo install -d -m 0700 /etc/blindport /var/lib/blindport
bash -c 'read -rsp "Blindport token: " token && printf "\n" && \
  printf "%s\n" "$token" | sudo install -m 0600 /dev/stdin /etc/blindport/token'

sudo blindportd \
  -wireguard \
  -backend={{ request.url.scheme }}://{{ request.url.netloc }} \
  -token-file=/etc/blindport/token \
  -state-dir=/var/lib/blindport

The host needs Linux kernel WireGuard and CAP_NET_ADMIN or equivalent privileges. The agent creates bpwg0, assigns the leased public /32, and installs source policy routing without replacing the host's main default route. Your application must listen on the assigned address or a wildcard socket; routed mode does not dial an upstream.

Tor SOCKS5 transport

Send backend and relay connections through a local Tor SOCKS5 listener. SOCKS mode fails closed and does not fall back to direct connections. WireGuard mode is rejected because kernel UDP cannot traverse SOCKS:

blindportd \
  -socks5=127.0.0.1:9050 \
  -backend=http://{{ onion_host or "BACKEND_ONION" }} \
  -relay={{ onion_host or "RELAY_ONION" }}:5443 \
  -server-name={{ relay_server_name }} \
  -token-file=/etc/blindport/token \
  -state-dir=/var/lib/blindport \
  -config=/etc/blindport/config.json

The client uses SOCKS authentication isolation for its outbound path and does not fall back to a direct connection when the proxy fails. SOCKS5 transport is available only in framed mode; the client rejects combining -socks5 with -wireguard because the kernel WireGuard UDP data plane cannot use the proxy. Tor can conceal the client's source address from the backend and relay, subject to endpoint and traffic-correlation risks. Blindport remains a reachability service, not an anonymity network.

Troubleshooting

no token or token file rejected
Confirm the file contains one token, is regular, owner-only, owned by the daemon user, and is not a symlink.
Subscription is missing
Confirm payment is settled and the subscription is active. Docker mode will discover it on the next poll; static and legacy modes still require a restart.
Domain payment is unavailable
For a customer domain, publish the one exact CNAME name and target from the dashboard and run the DNS check before creating an invoice.
TLS certificate fails
Confirm SNI matches the ordered hostname and the origin serves its complete certificate chain. Blindport does not issue the public service certificate.
HTTP-01 fails
Configure a separate plaintext challenge upstream and make sure the origin ACME client answers the requested token there.
WireGuard setup fails
Confirm Linux WireGuard support, CAP_NET_ADMIN, an active routed Blindport IP order, and no conflicts with interface, table, or rule-priority values.

Current limitations

  • Docker and active framed provisioning changes can take up to one configured poll interval. Static configuration and routed WireGuard changes require a restart.
  • One production client identity is enrolled per account. Docker labels can initiate one idempotent order and initial NWC payment, but cancellation and renewal policy remain account actions.
  • Established TCP sessions do not migrate across relay reconnects or DNS changes.
  • Framed UDP crosses the TCP/mTLS tunnel and may experience head-of-line blocking.
  • Routed mode supports Linux IPv4 /32 leases only. It does not manage host firewalls, application listeners, IPv6, or DNS.
